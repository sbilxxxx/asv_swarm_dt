# 考察 — 新盤面でのAI指揮官比較（qwen2.5:32b、20エピソード）

実行: 2026-08-30 23:44 開始 / 2026-08-31 完了。
コマンド:
```
node scripts/headless_run.js --scenario flag_defence_squadrons --blue llm --boat-mode llm \
  --model qwen2.5:32b --llm-url http://127.0.0.1:11434/v1 --episodes 20 \
  --out submission/measurements/qwen2.5-32b/qwen2.5-32b-20ep.jsonl \
  --decision-log submission/measurements/qwen2.5-32b/qwen2.5-32b-20ep-decisions.jsonl \
  --llm-log submission/measurements/qwen2.5-32b/qwen2.5-32b-20ep-calls.jsonl
```
条件: 守備側（blue）= 指揮官・艇とも qwen2.5:32b。攻撃側（red）は前回・今回とも scripted（ルールベース）で固定。
新盤面 `flag_defence_squadrons`（隻数8、各陣営 快速2・索敵1・重装1）。

出典データ: `console-20ep.txt`（エピソード要約）、`qwen2.5-32b-20ep.jsonl`（全ステップ位置ログ 42,422行）、
`qwen2.5-32b-20ep-decisions.jsonl`（指令スケジューラの判定 974件）、`qwen2.5-32b-20ep-calls.jsonl`（艇LLM生呼び出し 568件）。

## 1. 結果 — ルールベース統制群との比較

| | 防御成功 | 突破 | 時間切れ | 平均決着時刻 |
|---|---:|---:|---:|---:|
| ルールベース統制群（2026-08-30計測） | 16/20（80.0%） | 4/20（20.0%） | 0 | 31.5s |
| **AI指揮官+艇AI（本計測）** | **13/20（65.0%）** | **7/20（35.0%）** | 0 | 38.7s |

守備側をAI（指揮官・艇とも）にすると、防御成功率が80%→65%へ**15ポイント低下**した。
サンプルは各20エピソードのみで、旧盤面での前回計測（[game-design考察]参照、勝率のばらつきが約12ポイント）を踏まえると、
この15ポイント差は「誤差の範囲内」の可能性を否定できない。170エピソード規模の追試（後述）が必要。

### エピソード別内訳

- 防御成功13件の決着時刻: 16.2, 16.2, 16.3, 16.6, 16.9, 17.4, 17.8, 18.0, 18.6, 19.5, 19.7, 20.8, **34.2**s（平均19.1s）
- 突破7件の決着時刻: 69.3, 71.1, 74.6, 75.1, 75.9, 78.3, 81.6s（平均75.1s）

**二峰性はルールベース統制群と同じ形で保たれている**（早い快速艇クラスの決着 vs 遅い重装艇クラスの決着、という盤面設計 §game-design.md の「2段の時間割」が機能）。
崩れたのは二峰の「山」の中身ではなく、**どちらの山に落ちるかの比率**——AI守備側は突破側の山に落ちる回数が単純に増えた。

## 2. 診断 — どこで差が生まれているか

指令スケジューラの判定（decisions.jsonl）をデシジョン主体別に集計した。

| 主体 | 判定件数 | 適用（applied） | 保留（kept＝新規判断なし） | 推論レイテンシ（中央値） |
|---|---:|---:|---:|---:|
| 指揮官AI（blue-commander） | 85 | 82（96.5%） | 0 | 3,154ms |
| 攻撃側指揮官（red-commander、比較用） | 85 | 82（96.5%） | 0 | 0ms（scripted） |
| 守備艇AI（4隻合計） | 804 | 313（38.9%） | 473（58.8%） | 1,144ms |

**指揮官AIのパイプラインは健全**：適用されなかった3件はいずれも「エピソード終了時点で発効待ち（in-flight）」であり、
締切超過や解析失敗によるmissではない。指揮官は毎回きちんと命令を出せている。

**艇レベルのLLM呼び出しも技術的には失敗していない**。`calls.jsonl`には艇の呼び出し（`boatId`あり）と
指揮官の呼び出し（`boatId`なし・FORCE PICTUREプロンプト）が混在しており、正しく分けると
艇の呼び出しは483件・指揮官の呼び出しは85件（＝指揮官の判定件数85件と一致）。

- 艇の呼び出し483件はすべて `failure: null`。内訳は override（独自の回避行動）317件・65.6%、
  obey（指揮官命令に従う）166件・34.4%。「ok（現状維持）」は艇側には存在せず、指揮官側だけの選択肢だった
  （先の集計でこの2つを1本のカウンタに混ぜていたため、誤って「艇AIの15%がok」としていた。訂正する）。
- 指揮官の呼び出し85件はすべて `outcome: ok, failure: null`——指令スケジューラ側の適用率96.5%（§2冒頭）と
  合わせて、指揮官のLLM呼び出しは完全に健全だったと言える。

つまり艇AIは65.6%が指揮官命令を上書きして独自の迎撃行動を取り、34.4%が指揮官命令に従う判断をしている。
「自分で判断を上書きしない」がバグではなく意図的な選択であることは変わらないが、艇AIは受け身ではなく
むしろ積極的に独自判断している——それでもルールベース統制群に劣後した、という点が診断としてより厳しい。
（decisions.jsonl側の「kept」473件のうち一部は、そもそも決定周期のスケジューリングでLLM呼び出し自体が
発生しない周期だったことによるもので、残りがこの「obey」の反映）

旧盤面での前回計測（3アーム比較、slide8）で見つかった「移動命令の80.9%が直前と同座標への送り直し」という
**明確なバグ**（死んだwaypoint）とは性質が異なる。今回は技術的な故障は見当たらず、**守備艇AIの戦術的な判断の質**——
どこで迎撃するか、いつ指揮官の命令に従いいつ自分で判断すべきか——が、ルールベースの迎撃ロジックに比べて
劣っている可能性が高い。

## 3. 交絡要因（正直に書く）

この計測は「指揮官AI」と「艇AI」を**同時に**ルールベースからLLMへ切り替えている（`--blue llm --boat-mode llm`）。
そのため、80%→65%の低下が

- 指揮官の指示の質によるものか
- 艇の現場判断の質によるものか
- 両者の組み合わせ（指揮官とLLM艇の"噛み合わせ"）によるものか

を、この1本の計測だけでは切り分けられない。旧盤面での前回計測（slide8）は「指揮官のみLLM」の腕を含んでいたが、
新盤面ではまだ実施していない。指揮官のみ／艇のみをLLMにする切り分け計測は次のステップとして有効。

## 4.5 記録済みエピソードの対話的な再生（追記）

上記の静止画・動画に加えて、`replay-viewer/` に任意のエピソードを2D／3D／指揮官・艇AIの判断ログの
3画面で同期再生できるビュアーを実装した。`node -m http.server`等でリポジトリを配信し
`http://localhost:8000/replay-viewer/` を開き、「既定ログを読込」（このデータセットを自動取得）または
`qwen2.5-32b-20ep.jsonl`＋`-decisions.jsonl`＋`-calls.jsonl`を手動選択すると、エピソード選択・再生速度切替・
シークバー・判断ログのクリックシークができる。上のep1/ep3の軌跡・3D動画は、このビュアーで任意の
エピソード・任意の時刻を自分で確認できることの代わりにはならないので、両方を残す。
