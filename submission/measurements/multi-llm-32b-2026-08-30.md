# マルチLLM × 大規模モデル — 計測結果 2026-08-30

指揮官LLM 1体＋艇LLM 3体（計4体が同時に推論する構成）を、**8基GPU環境**で
モデル規模を上げて動かした記録。締切（08-30 24:00）時点で確定した内容だけを書く。

## 1. 実行環境（設計文書の記載との差分）

`docs/development-roadmap.md` §2 は計算資源を「手元 RTX 3060 12GB」「GPUクラスタは申請結果待ち」と
書いているが、**実際に本ランを回した環境は下記であり、記載の更新が要る**。

| 項目 | 実測値 |
|---|---|
| GPU | **NVIDIA RTX A5000 × 8基**（各 24,564 MiB / 合計 約192 GB） |
| ドライバ / CUDA | 595.84 / CUDA 13.2 / compute capability 8.6 |
| CPU / RAM | 64コア / 376 GiB |
| 推論サーバ | Ollama 0.33.2（`OLLAMA_NUM_PARALLEL=4`） |

`OLLAMA_NUM_PARALLEL=4` は本構成の同時発行数（指揮官1＋艇3）と一致する。

## 2. モデル選定 — なぜ qwen3:32b ではなく qwen2.5:32b か

当初 `qwen3:32b`（最新・32B）を選び 8基へ分散ロードできた（各GPU 約9〜10GB、合計75GB）が、
**全判断が `no usable decision` となり1件も成立しなかった。**

原因は thinking（reasoning）トークンの予算超過である。実測:

```
prompt_tokens=187  completion_tokens=3925  finish_reason=stop
reasoning=11,239文字   content={"move_to":[182,48],...}
```

艇1体の1回の判断に **reasoning だけで 3,925 トークン・応答まで2分超**を要した。
`--max-tokens 1500` でも本文に到達せず（`content:""`）、艇3隻・3秒間隔という運用条件に対して成立しない。

**thinking を切る試みは OpenAI 互換エンドポイントでは失敗した**（いずれも reasoning が出続けた）:

| 方法 | 結果 |
|---|---|
| `"think": false` を `/v1/chat/completions` に付与 | 無視される（reasoning 82トークン） |
| プロンプト末尾に `/no_think` | 効かない。モデルが制御語ではなく本文として読む |
| `"think": false` を `/api/chat`（Ollamaネイティブ）に付与 | **効く**（reasoning 無し・2トークンで即答） |

ネイティブAPIなら解決するが、`core/sim/agents/llm_http.js` は
「開発は Ollama、GPUサーバでは vLLM。どちらも同じエンドポイント形式」という可搬性を前提に
OpenAI互換で書かれている。**締切下でこの前提を捨てる改修は行わず、non-thinking の
`qwen2.5:32b` を採用した。**（thinking モデル対応は今後の課題として §5 に残す）

## 3. 動作結果 — qwen2.5:32b

1エピソード完走。`parseFailures=0` / `empty_content=0` / `transportFailures=0`。

| | qwen2.5:7b | **qwen2.5:32b** |
|---|---:|---:|
| wallTime（同一エピソード ep1） | 6.4 s | **20.6 s** |
| steps/s | 26.5 | 8.2 |
| 指揮官 meanLatency | 1,547 ms | **5,428 ms** |
| 艇 meanLatency | 735〜803 ms | **1,473〜2,041 ms** |
| 艇の判断 override / obey | 17 / 0 | **7 / 10** |

シム内時間（`simTime`）と実行時間（`wallTime`）は独立である。遅延は設定値
（指揮官 `latencyS=3s` / 艇 `1s`）で駆動されるため、**モデルを替えても実験条件は変わらず、
変わるのは実行にかかる実時間だけ**である（`docs/time-model.md` §2.5）。
本ランでも「発効時刻が `t_issue + latencyS` に一致」は 11/11 で成立している。

## 4. 創発の抽出

→ [`emergence/README.md`](emergence/README.md) に分離。ツールは
[`scripts/extract_emergence.js`](../../scripts/extract_emergence.js)（再現可能）。

要点だけ再掲する。

1. **指揮官は指示されていない配分を行う** — プロンプトは「重複を避けろ」「艦種を対応させろ」を
   要求していないが、標的の重複解消 100%、艦種の一致 100%（7b: 31/31、32b: 8/8）。
2. **モデル規模で役割の分化が現れた** — 同一 system prompt・同一モデルの艇3体で override 率が
   7b は全艇 100%（＝指揮系統が機能していない）、32b は 16.7% / 33.3% / **80.0%**（scout のみ独自判断）。
3. **override は「反抗」と「再確認」に分かれる** — 7b で反抗37件・再確認59件。ただし反抗の実例には
   自艇レーダーの数値と矛盾する理由づけがあり、**判断の質ではなく出力の不安定さに由来する疑いがある**。

いずれも少数エピソードでの観測であり、同条件反復による確認は行っていない。
