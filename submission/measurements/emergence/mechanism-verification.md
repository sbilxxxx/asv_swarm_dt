# マルチエージェント機構の成立検証

作成: 2026-08-31 / 対象ログ: `qwen2.5-32b-20ep-calls.jsonl`（20エピソード・LLM呼び出し 568回）

「創発が見えた」と言う前に、**そもそも指揮官と艇の間で指令の授受が成立しているのか**を
実ログで確かめた。主張ではなく、元ログの行に還元できる形で検証する。

構成: 指揮官LLM 1体（blue-commander）＋ 艇LLM 3体（def-runner-1 / def-runner-2 / def-scout）。
`def-heavy` は LLM ではなく、指揮官の命令を `BoatController` が直接追従する（`--boat-mode llm×3`）。
したがって階層は「LLM指揮官 → LLM艇3体 ＋ 非LLM艇1体」の混成である。

---

## V-1 指令は実際に艇へ届いているか — 届いている

エピソード1の時系列（指揮官の発令と、艇のプロンプトが実際に受け取った命令文）:

```
t= 0.0 [COMMANDER] def-heavy<-intercept int-heavy; def-runner-1<-intercept int-runner-1;
                   def-runner-2<-intercept int-runner-2; def-scout<-intercept int-scout
t= 0.0   [def-runner-1] 受領した命令= 'patrol (0, 0) r=200'      <- まだ古い命令
t= 0.0   [def-scout]    受領した命令= 'patrol (0, 0) r=200'      <- まだ古い命令
t= 3.0   [def-runner-1] 受領した命令= 'intercept int-runner-1'   <- 届いた
t= 3.0   [def-runner-2] 受領した命令= 'intercept int-runner-2'   <- 届いた
t= 3.0   [def-scout]    受領した命令= 'intercept int-scout'      <- 届いた
```

**t=0 に発令された命令が、艇のプロンプトに現れるのは t=3.0** である。
これは宣言値 `latencyS=3s` と正確に一致する（`t_apply = t_issue + latencyS`）。
「考えている間も時間は進む」という時間モデルが、艇の入力にそのまま反映されている。

t=0 の艇が `patrol` を見ているのは正しい。指揮官はまだ発令中で、その3秒間は
エピソード開始時の既定指示（`orders.js` の `applyDefaultOrders`）で動く仕様である。

## V-2 ID は実在するか — 幻覚ゼロ

指揮官のプロンプトには `OWN FORCE (truth)` と `ENEMY TRACKS` の名簿が載る。
そこに無い ID を指した指示を「幻覚」として数えた。

| 検査 | 結果 |
|---|---|
| 指揮官の総指示数 | 247 |
| 存在しない自艦を指名 | **0 (0.0%)** |
| 見えていない敵を標的化 | **0 (0.0%)** |
| 艇の override で自艇レーダー外を標的化 | **0 / 312 (0.0%)** |

**この 0% は防壁の効果ではなく、モデル自身が一度も外さなかった結果である。**
`boat_agent.js` の `parseBoatDecision` には「名簿外の標的は落とす」防壁があり、
`parse_orders.js` にも同種の防壁がある。落とされた指示があればそこに痕跡が残るが:

```
blue-commander: calls=85 ok=85 parseFailures=0 droppedOrders=0
def-runner-1:   calls=190 parseFailures=0
def-runner-2:   calls=192 parseFailures=0
def-scout:      calls=101 parseFailures=0
```

**568回の呼び出しで防壁が一度も発火していない。** 幻覚が起きて弾かれたのではなく、
そもそも起きていない。

## V-3 空応答・null・パース失敗は無いか — 無い

| 対象 | 呼び出し数 | 空の raw | result が null | 通信/推論の失敗 |
|---|---:|---:|---:|---:|
| 指揮官 | 85 | 0 | 0 | 0 |
| 艇 | 483 | 0 | — | 0 |

艇の outcome 内訳: `obey` 166 / `override` 317（判断不能はゼロ）。
失敗モード別でも `parse` / `timeout` / `connection` / `http_status` / `malformed_body` /
`empty_content` はすべて 0 である。

## V-4 `ignoredOrders` 40件は不具合か — 設計どおりの陳腐化

集計に出る `ignoredOrders=40` の発生源は `orders.js` の
「存在しない・**死んでいる**・陣営違いの艇への指示は捨てる」処理である。
V-2 のとおり幻覚は無いので、残る可能性は「発令から発効までの間に撃沈された」だけになる。

実際に、発効時刻に生存していなかった自艦を突き合わせた:

```
ep1 t_issue=10.0 -> t_apply=13.0: ignored=1  その時点で消えていた自艦=['def-scout']
ep1 t_issue=15.0 -> t_apply=16.0: ignored=1  その時点で消えていた自艦=['def-runner-1','def-scout']
...
死んだ自艦数 >= ignored 数 だったサイクル: 40/40
```

**40件すべてが説明できる。** 指揮官は3秒前の図を見て発令し、届いた時にはその艇が居ない——
これは不具合ではなく、この基盤が測ろうとしている現象そのものである。

## V-5 無意味に同じ指示を繰り返していないか — 繰り返しているが、正しい繰り返し

連続する采配 65 ペアのうち **49 ペア（75.4%）が完全に同一**だった。
これだけ見ると L0 で記録された欠陥（`move_to` の 80.9% が同一座標の再送＝死んだ waypoint）と
同じに見える。しかし**状況が変化したかで条件づけると評価が反転する**。

| | 命令そのまま | 命令変化 |
|---|---:|---:|
| **状況そのまま** | **49**（正しい安定） | 5（無駄な揺れ） |
| **状況変化** | **0 ★** | 11（正しい応答） |

**「状況が変わったのに命令が変わらなかった」ケースはゼロである。**
指揮官は自艦や敵トラックの増減に必ず反応している。

75.4% の同一が問題にならないのは、命令が `intercept <敵ID>` という**記号的な指示**だからである。
`orders.js` は発令時のトラック位置を `lastKnown` として同梱し、追従制御が毎tick解決し直す。
同じ標的を指し続けることは座標の陳腐化を意味しない。

### L0 の「死んだ waypoint」欠陥はこの盤面では再現していない

指揮官が使った action の内訳: `intercept` 243 / `move_to` **3** / `patrol` 1。
座標を直接書く `move_to` は 247件中3件（1.2%）しか使われておらず、
**欠陥のクラス自体がほぼ発生しない盤面になっている**。
（該当3件は ep17 t=10.0 で3隻に別々の座標を割り当てたもので、同一座標の再送ではない。）

## V-6 艇の応答は反射的すぎないか — 中間的

| | 判断そのまま | 判断変化 |
|---|---:|---:|
| **自艇レーダーそのまま** | 223 | 103 |
| **自艇レーダー変化** | 45 | 52 |

- 「レーダーが変わっても判断そのまま」45件は、多くの場合は妥当である
  （追っている標的が消えていなければ追い続けるのが正しい）。
- 「レーダーそのままで判断が変化」103件は temperature=0.7 由来の揺れを含む。
  ここは決定論性の観点で改善余地がある（温度を下げる価値がある）。

理由文の多様性: override 317件に対し**相異なる理由文 104種**。最頻でも21回で、
定型文のコピペではなく、状況に応じた文言が生成されている。

## 結論

**マルチエージェントの機構は成立している。** 検証した6点すべてで、
指令の授受・ID の実在性・応答性のいずれにも破綻が無かった。

一方で「成立している」ことと「賢い」ことは別である。
[`README.md`](README.md) 所見4 のとおり、この構成の勝率（65.0%）は
ルールベース統制群（170ep で 74.7%）を上回っていない。
**機構は正しく動いた上で、判断の質が勝率に結びついていない**というのが現状の位置づけである。
