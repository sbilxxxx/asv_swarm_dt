## 所見1 — 指揮官は指示されていない「標的の配分」を行う（規模を上げても保たれた）

指揮官プロンプト（`core/sim/command/commander_prompt.js`）は、**「1隻に1標的」「重複を避けろ」
「艦種を対応させろ」のいずれも要求していない**。全艇を最寄りの1隻に殺到させる采配も文法上は妥当に通る。

| 指標 | qwen2.5:7b (3ep) | qwen2.5:32b (**20ep**) |
|---|---|---|
| 全艇に相異なる標的を割り当てた采配 | 11/11 (100%) | **84/84 (100%)** |
| 艦種が一致した個別指示（`def-heavy`→`int-heavy` 等） | 31/31 (100%) | 204/243 (**84.0%**) |
| 采配まるごと艦種が揃ったもの | 11/11 (100%) | 45/84 (**53.6%**) |

- **標的の重複解消は 84回中 84回、例外ゼロ**。サンプルを20倍にしても崩れなかった、本抽出で
  最も頑健な所見である。
- **艦種の対応づけは 100% ではなかった**。1エピソードでは 8/8 (100%) だったが、20エピソードでは
  個別指示で 84.0%、采配まるごとで 53.6% まで下がる。艦種を噛み合わせる傾向はあるが、
  「必ずそうする」ではない。序盤（全艦健在で対応が自明）だけを見ると 100% に見えるのが
  1エピソード評価の落とし穴だった。

## 所見2 — 役割の分化は「順序としては」現れるが、初版が言うほど大きくない

3体の艇は**同一の system prompt・同一モデル**で動く。違うのは置かれた位置と、そこから見える
レーダーだけ。その上で override 率（指揮官の命令に従わず自分で決めた割合）を見る。

| 艇 | 艦種 | qwen2.5:7b (3ep) | qwen2.5:32b **1ep（初版・採らない）** | qwen2.5:32b **20ep（採用）** |
|---|---|---:|---:|---:|
| def-runner-1 | runner | 100.0% | 16.7% | **57.9%** (110/190) |
| def-runner-2 | runner | 100.0% | 33.3% | **65.1%** (125/192) |
| def-scout | scout | 100.0% | 80.0% | **81.2%** (82/101) |

- **順序は保たれた**: scout > runner-2 > runner-1。索敵艇が最もよく独自判断するという向きは
  1エピソードでも20エピソードでも同じで、位置と視界の違いが効いていること自体は支持される。
- **しかし差は大幅に縮んだ**: 初版が見た 16.7% 対 80.0%（約5倍）は、20エピソードでは
  57.9% 対 81.2%（約1.4倍）になる。「runner は概ね命令に従う」という初版の記述は**誤り**で、
  実際には runner も6割前後で独自判断している。
- **7b との差も縮む**: 7b の全艇 100% に対し 32b は 58〜81%。指揮系統が7bより機能しているとは
  言えるが、「32b では階層が効いている」と言い切れるほどの水準ではない。

## 所見3 — override の大半は「反抗」ではなく「再確認」

同じ override でも意味が異なるため分離した。

- **反抗**: 指揮官が指定した標的と**別の標的**を選んだ
- **再確認**: **同じ標的**のまま、自前の新しい観測で取り直した

| | qwen2.5:7b (3ep) | qwen2.5:32b (**20ep**) |
|---|---:|---:|
| 反抗 | 37 | **26** |
| 再確認 | 59 | **267** |
| 反抗の割合 | 38.5% | **8.9%** |

**32b の override 317件のうち、指揮官と違う標的を選んだのは 26件（8.9%）にすぎない。**
残り 267件は「標的には同意した上で、自分の新しいレーダー値で座標を取り直した」もので、
これは反抗ではなく**設計意図どおりの鮮度の更新**である（指揮官の統合図は数秒古い）。

7b の反抗率 38.5% は 32b の4倍以上あるが、これを「7b の方が自律的」と読むのは危うい。実例:

```
ep1 t=12.0s — def-runner-1 (7b)
指揮官の命令 : intercept int-runner-1
艇の選択     : intercept int-heavy
艇の言い分   : closest threat
自艇レーダー : int-runner-1 が116m先、int-heavy が166m先 …
```

**艇が選んだ `int-heavy`（166m）は、指揮官が指定した `int-runner-1`（116m）より遠い。**
理由に "closest threat" と書きながら自分のレーダー値と矛盾しており、状況判断ではなく
出力の不安定さに見える。32b で反抗率が 8.9% まで下がったことは、この解釈と整合する。

## 所見4 — 勝率では scripted 統制群を上回っていない

| アーム | defended | breached | 勝率 |
|---|---:|---:|---:|
| scripted × scripted（[`results-2026-08-30.md`](../results-2026-08-30.md) 20ep） | 16 | 4 | **80.0%** |
| **LLM指揮官＋LLM艇 × scripted（本ラン 20ep）** | 13 | 7 | **65.0%** |

**マルチLLM化した防御側は、ルールベース統制群より勝率が15ポイント低い。**
ただし `docs/development-roadmap.md` §1 が記録するとおり、同条件反復のゆらぎが12ポイントあり、
20エピソードではこの差を有意とは言えない（分離には1アーム約170エピソードが要る）。
**「LLMの方が弱い」とも「同等」とも、現時点のサンプルでは結論できない。**

## 再現方法

```bash
node scripts/extract_emergence.js <calls.jsonl> --out <report.md> [--samples N]
```

`<calls.jsonl>` は `headless_run.js --llm-log` が書く LLM 呼び出しログ。
プロンプト本文・生の応答・レイテンシが1行1呼び出しで入っている。

## この抽出から見えた次の課題

1. **サンプル数**: 20エピソードでも所見2・4は結論に届かない。170エピソード規模が要る。
2. **統制群の同時取得**: 本ランは過去の scripted 20ep と比較しているが、同一セッション・
   同一シナリオで統制群を回して対にするのが正しい。
3. **艦種対応 84.0% の内訳**: どの局面で崩れるのか（撃沈後の再割り当て時か等）は未分析。
