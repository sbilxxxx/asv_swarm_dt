# マルチVLMエージェントの収容設計 — VRAM は KV キャッシュで決まる

> 作成: 2026-09-06
> 実測環境: `gpu-sv-007`（RTX A5000 × 8 / 各24.5GB / 計196GB）・Ollama 0.33.2
> 共有マシンの取り決め: [`/tmp/GPU-USAGE-CONVENTION.md`](file:///tmp/GPU-USAGE-CONVENTION.md)（掲示）
> 計測ツール: [`scripts/suggest_num_ctx.js`](../scripts/suggest_num_ctx.js)（マルチエージェント実験側が作成）
> 実行時の検証: [`core/sim/agents/context_budget.js`](../core/sim/agents/context_budget.js)

---

## 1. 結論 — 律速は計算ではなく KV キャッシュである

**「何体のVLMエージェントを同時に走らせられるか」を決めるのは GPU の演算能力ではなく、
`num_ctx × 並列スロット数` で先に確保される KV キャッシュの VRAM である。**

実測（2026-09-06）:

| モデル | num_ctx | 並列 | 占有 VRAM | 内訳 |
|---|---:|---:|---:|---|
| `qwen2.5vl:7b`（素） | 128,000 | 8 | **85.9 GB** | 重み約6GB ＋ KV **58.7GB** ＋ vision tower ＋ 計算バッファ |
| `qwen2.5vl-7b-ctx3k`（派生） | 3,072 | 2 | **5.64 GB** | 重み約6GB のほぼそれだけ（KV は 0.34GB） |

**同じ7Bモデルで 15分の1。** 重みは 6GB しかないのに 86GB を占有していた原因は全部 KV キャッシュである。
このとき `nvidia-smi` の GPU 使用率は **0%** だった——計算していないのに VRAM だけを掴んでいた。

KV キャッシュの算術（モデルの形から決まる。`/api/show` の `model_info` で取れる）:

```
KV/token = 2(K,V) × block_count × kv_head数 × head_dim × 2バイト(f16)
qwen2.5vl:7b → 2 × 28 × 4 × 128 × 2 = 57,344 バイト = 56 KB/token

num_ctx=128,000 → 7.34 GB/スロット × 8 = 58.7 GB
num_ctx=  3,072 →  0.17 GB/スロット × 2 =  0.34 GB
```

## 2. num_ctx を決める仕組み

### 2.1 両側に事故がある

| | 起きること |
|---|---|
| **小さすぎる** | **無警告でプロンプトが切り捨てられる。** 推論サーバはエラーを返さず、画像や状況図の一部が欠けた入力に普通に答える。「VLM の判断が悪い」ように見えるが、実際には見せた情報が届いていない——**実験ログからは判別できない、最悪の種類の故障** |
| **大きすぎる** | VRAM を KV で食い潰し、同時に走らせられるエージェント数が減る。実際にこれで**実験が7時間空回りした**（マルチエージェント実験側の報告） |

したがって num_ctx は「大きめにしておけば安全」な値ではなく、**実測から決めて実行時に検証する**対象である。

### 2.2 決め方（推定ではなく実測）

Ollama には `/api/tokenize` が無い（0.33.2 で 404）。代わりに **`num_predict=1` で1回叩き、
応答の `prompt_eval_count` を読む**のが正確で、これを `scripts/suggest_num_ctx.js` が行う。

```bash
# 実際に使うシステムプロンプト・状況図・画像で測る（ここを実物にしないと意味が無い）
node scripts/suggest_num_ctx.js --model qwen2.5vl:7b --url http://127.0.0.1:11434 \
  --system-file /tmp/nav_system.txt --prompt-file /tmp/nav_user.txt \
  --image logs/vlm-nav-.../c03.png --max-tokens 400 \
  --create qwen2.5vl-7b-ctx3k
```

単艦VLM航行ビュアーの実測（640×360 PNG 1枚）:

```
prompt      : 1,520 tok  = テキスト 486 + 画像 1,034
max_tokens  :   400
必要量      : 1,920 tok
推奨 num_ctx: 3,072（余裕率 1.5x → 1024の倍数へ切り上げ）
```

**画像はテキストより桁違いに高い。** 486 tok のテキストに対し画像1枚で 1,034 tok——
「プロンプトは数百トークンだから 8192 で十分」というテキスト側の勘は VLM に持ち込めない。
解像度と枚数がそのまま効く（望遠カメラを足して2枚にすれば +1,034 tok）。

### 2.3 反映のしかた — 2経路ある

| 経路 | 方法 | 向く場面 |
|---|---|---|
| **派生モデル**（採用） | `FROM <base>` ＋ `PARAMETER num_ctx N` の Modelfile。`suggest_num_ctx.js --create` が作る | Ollama の OpenAI 互換経路（`/v1/chat/completions`）でも効く。**ブラウザから同一オリジン中継で叩く本ビュアーはこちら** |
| リクエスト毎の指定 | Ollama ネイティブ `/api/chat` の `options.num_ctx` | 1本のサーバで用途ごとに窓を変えたいとき。ただし OpenAI 互換経路では無視される |

重みのレイヤーは共有されるので、派生モデルを作ってもディスクはほとんど増えない（マニフェストだけ）。

### 2.4 実行時の検証（宣言が正しかったかを毎回確かめる）

`core/sim/agents/context_budget.js` の `describeContextUsage()` が、応答が返した実測
`prompt_tokens` と宣言した `num_ctx` を突き合わせて3値で判定する。

| 判定 | 意味 |
|---|---|
| `ok` | 収まっている |
| `tight` | 余裕10%未満。プロンプトが少し伸びると切り捨てへ落ちる |
| `overflow` | **切り捨てが起きた可能性がある。この判断は信用してはいけない** |

**判定するだけで num_ctx は変えない。** 実行中に変えると推論サーバがスロットを作り直し、
ランの途中で VRAM 使用量と速度が変わってしまう——[`time-model.md`](time-model.md) §2.5 と同じ規律
（実測は記録に留め、設定値へ書き戻さない）。

## 3. 何体走らせられるか（収容計算）

同時に推論できる数 = **1つのモデルに与えた並列スロット数**（Ollama の `OLLAMA_NUM_PARALLEL`）。
必要 VRAM は概算で `重み + KV/スロット × スロット数`。

`num_ctx=3072` を前提にした見積り（A5000 = 24.5GB / GPU）:

| モデル | 重み(Q4) | KV/スロット | 8スロット時の合計 | 収まる GPU 数 |
|---|---:|---:|---:|---:|
| 7B VLM | 約6 GB | 0.17 GB | 約7.4 GB | 1 |
| 32B VLM | 約20 GB | 0.79 GB | 約26 GB | 2 |

**つまり ctx を絞れば、32B の VLM に8体ぶんの同時スロットを与えても2基で足りる。**
絞らなければ 7B 1本で 4基ぶんを食う。マルチエージェント化の可否はこの一点で決まる。

### 3.1 「モデルを増やす」のが最も高い

VRAM は **モデル本数に線形**に増える（重みが各々必要なため）。実際、素の `qwen2.5vl:7b`（85.9GB）と
`qwen2.5-7b-ctx8k`（8.7GB）の2本で 95GB を占有していた。

したがって役割（指揮官・艇・航海士）は**プロンプトで分け、モデルは共有する**のが安い。
別モデルが要るのは能力差が本質的なときだけ——実測では
「thinking 系か非thinking系か」がその唯一の例だった
（[`l1-vlm-navigator-implementation-2026-09-05.md`](l1-vlm-navigator-implementation-2026-09-05.md) §3.3）。

### 3.2 同時推論数の上限はシム側で既に保証されている

必要スロット数を決めるのはシム側であり、その上限は既に構造で決まっている。

| 仕組み | 効き方 |
|---|---|
| `DecisionScheduler` の不変条件 I2「1 decider につき同時1推論」 | **同時推論数 ≤ decider 数**。これが VRAM 要求の上界を与える |
| `register(id, { firstIssueAtT })` | 判断の**位相をずらす**。同じ `intervalS` の艇を同時刻に発行させるとピークが decider 数になるが、位相をずらせば平均へ近づく |
| `deadlineS` / `onMiss` | スロット待ちで発効が間に合わなかったときに、実験を壊さず「不成立」として記録する安全弁 |
| `captureSize`（`camera_sensor.js`） | 画像解像度を固定し、表示ウィンドウの大きさがトークン数＝KV に混ざるのを防ぐ |

L0 の実測（20エピソード）では指揮官84コール／艇483コール。**艇側が85%**なので、
マルチVLM化でスロットを要求するのも艇側である。

### 3.3 スループットの確認

必要判断レート = `艇数 / intervalS`。8隻・`intervalS=10s` なら 0.8 判断/秒。
実測の推論時間は 7B・画像1枚で p50 1.7〜2.3 秒なので、2スロットで 0.9〜1.2 判断/秒——
**8隻ぶんをかろうじて捌ける**。32B は遅いので実測が必要。

なお推論が遅れてもシムの結果は変わらない（発効遅延は設定値 `latencyS` が唯一の出所）。
変わるのは**ランの実時間だけ**である。

## 4. 共有マシンでの運用（この機の取り決め）

| グループ | GPU | ollama | 用途 |
|---|---|---|---|
| vlm | 0,1,2,3 | `127.0.0.1:11434` | VLM / 画像航行（本ビュアー） |
| sim | 4,5,6,7 | `127.0.0.1:11435` | マルチエージェント実験 |

NVLink が無く GPU0-3 と GPU4-7 が別 NUMA のため、この境界で分けている。
vlm 側の起動:

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 OLLAMA_HOST=127.0.0.1:11434 \
OLLAMA_MODELS=$HOME/.local/ollama/models \
OLLAMA_NUM_PARALLEL=2 OLLAMA_KEEP_ALIVE=20m \
nohup ~/.local/ollama/bin/ollama serve > /tmp/ollama_vlm.log 2>&1 &
```

- `OLLAMA_NUM_PARALLEL=2` — ビュアーは逐次1本なので2で足りる。増やすと KV が倍化する
- `OLLAMA_KEEP_ALIVE=20m` — 以前は 2h で、GPU使用率0%のまま95GBを掴み続けていた
- ポートは 11434 のままなので、`serve_vlm.js` の既定（`--upstream http://localhost:11434`）は変更不要

**確認済み（2026-09-06）**: 上記設定の `ollama serve` が 11434 を保持し、
`qwen2.5vl-7b-ctx3k` が **5.64GB** で GPU 0-3 の範囲に載ること、
sim 側（11435 / GPU4-7）に影響しないことを実測した。

## 5. 未検証・残っていること

- **32B VLM での実測がまだ無い。** §3 の 26GB は算術による見積りで、実測していない
- 望遠カメラ（2枚目の画像）を足したときの `num_ctx` 再測定
- `describeContextUsage` の判定を航海士・艇・指揮官の全 decider の統計へ出す配線（現在は航海士のみ）
- 複数モデルを跨ぐ実験キューでの明示アンロード（`gpujob` 側が実装済み。こちらからは呼んでいない）
