# L0 実験ログ（指揮官アーム比較）

> 実施: 2026-08-14 / 環境: AMD Ryzen 7 5700X・RTX 3060 (12GB)・Windows 11 / Ollama 0.32.6 / モデル: `qwen2.5:7b`（Q4_K_M）
> 計画: [`l0-llm-agent-plan.md`](l0-llm-agent-plan.md) Task 10 / 時間設計: [`time-model.md`](time-model.md) v2.0
> 実測の前提: [`llm-probe-measurements-2026-08-13.md`](llm-probe-measurements-2026-08-13.md)（Task 1）
> 条件: **3隻**（防御2・侵入1）・**25エピソード/アーム**・`intervalS=10s`・`latencyS=3s`・`deadlineS=∞`・`onMiss=keep-current`・`temperature=0.7`

**この文書は記録（実測ログ）であり、ルール（設定値）ではない**（time-model §2.5）。
そして**この実験の主要な結論は「この N では LLM 指揮官と統制群を区別できない」という帰無**である。
先に読むべき節は §6「この N で言えること・言えないこと」。

## 1. 計画からの条件変更（3点）

| 計画 | 実施 | 理由 |
|---|---|---|
| `--boats 6` | **`--boats 3`** | 6隻の統制群は **97勝3敗**で、防御側アームに伸びしろが3点しか無い。改善も悪化も示せない。3隻の統制群は **78勝22敗**（100エピソード、2回実行してバイト単位で一致）で、**両方向に余地がある唯一の構成**。9隻は逆に 1勝99敗で床に張り付く |
| 10エピソード/アーム | **25エピソード/アーム** | 10 では何も分離できない。25 でも足りない（§6）が、実時間の上限がここだった |
| `qwen3:8b` | **`qwen2.5:7b`** | このマシンに `qwen3:8b` は無い。Task 1 の実測で JSON スキーマ遵守 48/48・ウォーム 2.1s だった本命モデル |

エピソード番号は擬似乱数ではなく、侵入側の接近角を決める決定論的な関数の引数である。
したがって**全アームのエピソード1〜25は同一の初期条件の集合**であり、アーム間の比較は**対応のある比較**になる。

## 2. 勝敗

| アーム (blue vs red) | defended | breached | timeout | 防御側勝率 | 実時間 | steps/s |
|---|---|---|---|---|---|---|
| **A** — scripted vs scripted（統制群） | 19 | 6 | 0 | **76.0%** | 0.23 s | 100,390（1隻あたり 33,464） |
| **B** — **llm** vs scripted | 22 | 3 | 0 | **88.0%** | 385.4 s | 57.6（19.2） |
| **C** — **llm** vs **llm** | 25 | 0 | 0 | **100.0%** | 380.4 s | 37.2（12.4） |

参考: 統制群の100エピソード基準値は **78勝22敗（78.0%）**。上表の25エピソードは同じ系列の先頭25本である。

**この 76.0 → 88.0 → 100.0 という並びを「改善」として読んではいけない。** 理由を §2.1 と §2.3 に書く。

### 2.1 この差は誤差の大きさである（同条件の反復3本）

アームBを**条件を1つも変えずに3回**回した。温度0.7なので、同じ条件でも結果は動く。

| アームBの反復 | defended/25 | 勝率 | ログ |
|---|---|---|---|
| r1（§2の表の行） | 22 | **88.0%** | `logs/l0-ls*` |
| r2 | 19 | **76.0%** | `logs/l0-ls-r2*` |
| r3（検証で追加） | 21 | **84.0%** | scratchpad `verify-ls-r3*` |
| **プール** | **62 / 75** | **82.7%** | |

**同条件反復の幅は 12.0 ポイント（88.0 / 76.0 / 84.0、sd 6.1）。統制群に対する「改善」12.0 ポイントと同じ大きさである。**
r2 に至っては統制群と同じ 76.0% で、たまたま r1 を代表値に選ぶと「+12点の改善」に、r2 を選ぶと「差ゼロ」に見える。

エピソード単位でも同じことが起きている。同条件の反復どうしで結末が食い違ったエピソード数:

| 比較 | 食い違い |
|---|---|
| r1 vs r2 | 9 / 25（36%） |
| r2 vs r3 | 8 / 25 |
| r1 vs r3 | 5 / 25 |

同じ設定・同じ初期条件でも4本に1本以上は結末が反転する。**LLM アームはエピソード単位で決定論ではない**（統制群 A は決定論で、2回実行してバイト単位一致を確認済み）。

### 2.2 統計（アームB r1 と統制群Aの対応のある比較）

| 検定 | 値 |
|---|---|
| McNemar（対応あり・厳密二項、b=5 c=2） | **p = 0.4531** |
| Fisher 正確検定 22/25 vs 19/25 | p = 0.4635 |
| Fisher 正確検定 22/25 vs 統制群 78/100 | p = 0.4022 |
| Wilson 95% CI: 22/25 | [70.0, 95.8] % |
| Wilson 95% CI: 19/25 | [56.6, 88.5] % |
| Wilson 95% CI: 78/100（統制群） | [68.9, 85.0] % |
| Wilson 95% CI: アームBプール 62/75 | [72.6, 89.6] % |
| 対応のある平均差（B 3反復プール − 統制群） | +6.7 pt、95% CI **[-8.2, +21.5]** pt |

信頼区間はすべて重なる。**76.0% → 88.0% は有意差ではない。**

連続量でも同じ結論だった。侵入艇の防護対象への最接近距離を対応のある Wilcoxon で比較して p = 0.783（平均差 +12.7 m）、150 m 以内のニアミス回数 8/25 対 3/25 で McNemar p = 0.180。**N=25 でアームを分離できた指標は1つも無い。**

### 2.3 アームCの 100% は「LLM防御側が強い」ではない

アームCが無失点なのは、**LLM 侵入側が scripted 侵入側より弱いから**である。侵入側の150件の指示の内訳が理由を示している。

| アームC 侵入側（LLM）の指示 150件 | intercept | patrol | move_to |
|---|---|---|---|
| 件数 | **69** | 2 | 79 |

`intercept` は防御側トラックを追う指示である。**侵入側の46%が防護対象ではなく護衛艇を追いかけている。**
scripted 侵入側は常に防護対象へ直進し、迂回だけをエピソードごとに変える。エピソード長にも出ていて、アームCは中央値 56.3 s・最大 77.0 s で、長期戦（＝防御側を振り切って粘る展開）が1本も無い。

**アームCは3つ目のアームとしては有効だが、測っているのは赤の弱さである。防御側の比較として意味があるのはアームB対統制群だけ。**

### 3.1 発効時刻の検証（time-model §4 の中心的な要求）

| アーム | `t_issue + 3s` に厳密一致 | 同 tick で解放された keep | 最大ずれ | blocked | missed |
|---|---|---|---|---|---|
| A | 464 / 464 | 0 / 0 | 1.7e-13 s | 0 | 0 |
| B | 456 / 456 | 0 / 0 | 1.7e-13 s | 0 | 0 |
| C | 296 / 296 | 0 / 0 | 1.7e-13 s | 0 | 0 |
| A/B 実験・検証の4本 | 531/531・458/458・510/510・486/486（うち keep 1/1） | | 1.7e-13 s | 0 | 0 |

**合計 2,701 サイクルすべてが `t_issue + latencyS` にぴったり発効した。**
最大ずれ 1.7e-13 s は `dt=0.1 s` に対する浮動小数の丸め誤差であり、`T_EPS` の設計どおり。
`blocked=0` / `missed=0` は headless 実行器の仕様（発行を await してから物理を進める）どおりで、time-model §9 の非対称性が実装で成立していることの確認になる。

**scripted アームも同じ `latencyS` の床に従っている**（アームA も 464/464 が `t_issue+3s`）。
これにより「LLM 対 scripted」の比較から**推論速度という交絡が排除されている**（time-model §9）。
比較しているのは采配の質だけである——それが N 不足で見えない、というのが §2 の結論。

## 4. 采配の質

### 4.1 指示の内訳

| 実行 | intercept | patrol | move_to | 計 |
|---|---|---|---|---|
| B 防御側 r1 | 142（30.6%） | 95（20.5%） | 227（48.9%） | 464 |
| B 防御側 r2 | 141 | 95 | 229 | 465 |
| C 防御側 | 99 | 53 | 148 | 300 |
| C 侵入側 | 69 | 2 | 79 | 150 |

呼び出しは毎回 `intent` を伴い、指示は統合図に出てくる艇名・トラック名だけを参照していた（droppedOrders=0）。
陣営越えの指示（赤の艇に青が命令する類）は1件も無い。パースは 1,554 件中 1,553 件成功。

### 4.2 目立つ欠陥 — 「死んだ waypoint」

**`move_to` の再送。** 防御側は同じ座標の `move_to` を次のサイクルでもそのまま出し直す。

| 指標（B 防御側） | r1 | r2 |
|---|---|---|
| 直前と**バイト単位で同一**の `move_to` を再送した割合 | 160/198 = **80.8%** | 161/199 = **80.9%** |
| どの可視トラックからも 200 m 以上離れた `move_to` の割合 | 81/227 = **35.7%** | 86/229 = **37.6%** |

`move_to` は固定点なので、目標が動けば指示は10秒ごとに古くなる。実ログでは次のようになっていた:

```
logs/l0-ls-calls.jsonl ep1  t=0〜50  defender-1: move_to@(800,300) を6回そのまま再送
                                     その間に最寄りトラックは 225m → 602m まで離れる
```

追尾が要る場面では `intercept`（トラックを追い続ける）を使うべきところで、モデルは「最後に見えた位置」へ固定点を置き、それを更新しない。**L0 で最も明確に見えた采配の欠陥はこれである。**

## 5. `ORDERS_SCHEMA` の A/B（1行追加して効果を測る）

§4.2 の欠陥を狙って、システムプロンプトの JSON ブロックの直後に1行だけ足した。

```js
'intercept keeps chasing that track as it moves; move_to is a fixed point that never updates; patrol circles a fixed centre.',
```

温度0.7では1本ずつでは効果と揺らぎを分離できないので、**各版2反復ずつ（4 × 25エピソード）** 回した。条件・エピソード系列・モデル・温度はすべて同一。

| | before r1 | before r2 | **before プール** | after r1 | after r2 | **after プール** |
|---|---|---|---|---|---|---|
| defended/breached | 22/3 | 19/6 | **41/50** | 18/7 | 20/5 | **38/50** |
| 勝率 | 88.0% | 76.0% | **82.0%** | 72.0% | 80.0% | **76.0%** |
| (a) どの可視トラックからも 200m 超の `move_to` | 81/227 = 35.7% | 86/229 = 37.6% | **167/456 = 36.6%** | 181/275 = 65.8% | 186/258 = 72.1% | **367/533 = 68.9%** |
| (b) 直前と同一の `move_to` の再送 | 160/198 = 80.8% | 161/199 = 80.9% | **321/397 = 80.9%** | 243/245 = 99.2% | 223/229 = 97.4% | **466/474 = 98.3%** |
| 指示の内訳 intercept/patrol/move_to | 142/95/227 | 141/95/229 | 30.6 / 20.5 / 48.9 % | 212/65/275 | 186/76/258 | 38.4 / 11.8 / 49.8 % |

計画が指定した指標は (a)。(b)（同じ waypoint をそのまま再送）は「死んだ点」のより素直な読み取りとして追加した。

### 判定: **この1行は有害。採用せず、`commander_prompt.js` は変更前の状態へ戻した。**

- **勝率の差は読めない。** 同一版の反復どうしが12ポイント違う（88% と 76%）以上、版間の6ポイント差（82.0% → 76.0%）は揺らぎの内側にある。プール50本ずつの2標本検定でも p ≈ 0.6。
- **行動指標は揺らぎではなく、悪化した。** 各版の2反復は互いに近く、2つのクラスタは重ならない: (a) 35.7 / 37.6% → 65.8 / 72.1%（**+32ポイントの悪化**）、(b) 80.9% → 98.3%。
- 指示の内訳は狙いどおり patrol → intercept へ動いた（patrol 20.5% → 11.8%、intercept 30.6% → 38.4%）が、同時に `move_to` を「**あえて固定したい最終確認位置**」の道具として使い始め、その点をほぼ毎サイクル再送するようになった。

```
logs/l0-ls2-calls.jsonl ep1  t=10〜40  defender-2: move_to@(768,267) を4回再送
        intent: "move defender-2 to intruder last seen position"
        → 以降 "Continue current orders." / "Maintain patrol and proceed to waypoint."
```

**教訓**: 動作の意味を説明する1行では直らない。必要なのは「すでに出した waypoint を出し直すな」という禁止か、防御側のスキーマから `move_to` を落とすこと。どちらも L0 の範囲を超える（Phase 2 側の課題）。

`core/sim/command/commander_prompt.js` が実験前とバイト単位で一致することは `diff` で確認済み。テストも全件 PASS。

## 6. この N で言えること・言えないこと

### 言えること

- **時間フレームワークは実測で成立している。** 2,701 サイクルすべてが `t_issue + latencyS` に厳密発効。scripted と LLM が同じ遅延の床を共有している（交絡の排除）。
- **LLM 指揮官は実運用の耐久性を持つ。** 1,554 コールで transportFailures 0・parseFailures 1・keptOrders 0.06%。150 エピソード・実時間42分の連続実行で落ちなかった。
- **`latencyS=3s` は妥当。** 実測 1.65〜2.11 s 平均、最大 3.20 s。
- **采配には具体的で再現する欠陥がある**（§4.2 の move_to 再送 80.9%）。これは N に依存しない行動指標で、反復間で安定している。
- **プロンプトの1行が行動指標を大きく動かす**ことは測定できた（+32 ポイント、反復間で非重複）。

### 言えないこと

- **「LLM 指揮官は統制群より強い」とは言えない。** 76.0% → 88.0% は同条件反復の幅（12.0 ポイント）と同じ大きさで、McNemar p = 0.45、95% CI [-8.2, +21.5] pt。**帰無を棄却できない。**
- **「LLM 指揮官は統制群より弱い」とも言えない**（同じ理由）。
- **アームCの 100% を防御側の性能として読んではいけない**（§2.3）。
- **`ORDERS_SCHEMA` の1行が勝率に効いたとも効かなかったとも言えない**（行動指標には効いた。悪い方向に）。

### 必要な N

25 エピソードで 76% → 88% を検出する検出力は約 **19%**。80% の検出力には **1アームあたり約170エピソード**が要る。
LLM アームは1エピソード約15秒（実時間）なので、170エピソード×2アームで **約1.4時間**。**これは実行可能で、L2（スイープ）の設計に織り込む。**
統制群は 108,000 steps/s で回るので、比較対象側のコストはゼロと考えてよい。

## 7. 次段への含意

**`intervalS=10s` は指揮官には妥当だが、長い。** 1エピソード（中央値55〜69シム秒）で発行は5〜7回しかない。
采配の質を勝率で測るなら、判断機会を増やすか（`intervalS` を縮める）、エピソードを長くする必要がある。
ただし `intervalS` を縮めると発行レートが上がり、Phase 2 のスループット問題（下記）に先に当たる。

**Phase 2 のゲートは依然として未達。** [llm-probe §5](llm-probe-measurements-2026-08-13.md) の判定（艇プロンプトで 1.94 回/秒、ゲート 6.6 回/秒に **3.4倍不足**）は今回の実測でも変わらない。
L0 の指揮官2体（0.2 回/シム秒）は余裕で回るが、艇6隻を足すと 2.2 回/シム秒になり、`TIME_SCALE=3` のブラウザは推論待ちで埋まる。
**Phase 2 の計画書で「`TIME_SCALE` を下げる／`intervalS` を延ばす／隻数を絞る／GPU 環境」の4択を決める必要がある。**

**`OLLAMA_NUM_PARALLEL` は依然 1 のまま。** 今回の全ランは既定サーバ（並列度1）で回した。アームCは指揮官2体が直列化しているぶん遅い（37.2 steps/s 対 アームBの 57.6）。
4 に設定すれば2体同時の実時間が 3.8 s → 2.5 s に縮む（[llm-probe §4.3](llm-probe-measurements-2026-08-13.md)）。**環境側の設定であり、シム結果は変わらない**（time-model I4）。

**`deadlineS` は L0 では一度も発火していない**（missed=0、既定 ∞）。有限締切の経路はテストとブラウザで検証済みだが、実験としては未使用。
Phase 2 で decider が増えれば「誰か1人が詰まる確率」が上がるので、そこで初めて実験軸になる（time-model §12.5「段階適用」）。

**L1（VLM）に向けて。** `latencyS` は宣言合成（`[render] → [infer]`）へ拡張する設計になっており、L0 では単一ステージのまま使った。
ステージ別の実測 t_wall は既に記録されている（`--decision-log` の `stage=infer`）ので、render を足す準備はできている。
