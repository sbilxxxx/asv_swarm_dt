# デジタルツインの品質担保メソッド

- 作成: 2026-08-07 / v1
- 背景: 構文チェック・JSON検証・HTTP応答確認だけで「動作確認済み」と報告したところ、実際のレンダリング画面には複数の重大な不具合（カメラ位置バグ、スケール不整合、Zファイティング、レイアウトバグ、座標計算バグ）があった。**静的チェックは「例外を投げずに動く」ことしか保証しない。「意図した通りに見える・動く」ことは目視でしか確認できない。**

## 今回発見した不具合の分類（実例）

| 分類 | 実例 | 静的チェックで検知できたか |
|---|---|---|
| 状態共有バグ | 表示用カメラとセンサー用カメラを同一オブジェクトで使い回し、センサー取得時の位置変更が表示側に漏れて画面が船体で埋まった | できない（例外なし） |
| スケール不整合バグ | シナリオの地理スケール（実際の東京湾規模、数十km）とエージェントの行動スケール（レーダー1500m、巡航速度6m/s）が噛み合わず、レーダーが常に「contacts: 0」だった | できない（数値は計算できている） |
| ジオメトリ配置バグ | 陸地と水面が同一高度（y=0）で重なりZファイティングを起こし、迷彩状のノイズ模様になった | できない |
| CSS/レイアウトバグ | canvasの内在サイズ（デフォルト300×150）がflexレイアウトと循環し、実際の描画範囲が想定と大きくずれた | できない |
| 座標系バグ | レーダーの絶対方位をそのまま操舵量として使っており、自艇の針路を考慮していなかった | できない（NaNにもならない） |

いずれも「コードは構文的に正しく例外も投げない」が「意図通りには動いていない」典型例であり、目視（またはそれに相当するピクセル単位の確認）以外では発見できなかった。

## 開発メソッド：スクリーンショット駆動のPDCA

### 手順

1. **Plan/Do（実装）**: 変更を加える
2. **Check（自動キャプチャ）**: [`​.devtools/screenshot.js`](../.devtools/screenshot.js) でheadless Chromeを起動し、実際のレンダリング結果をPNGで取得する。同時にブラウザconsoleのエラー・警告も収集する
3. **目視確認**: 取得したPNGを確認する。「動いているはず」ではなく「実際に何が描かれているか」で判断する
4. **原因特定（実測）**: 見た目の異常から逆算してコードを疑う。憶測で直さず、`.devtools/debug.js`のようなワンオフスクリプトで、実行中のシーングラフ・カメラ位置・エンティティ座標を`page.evaluate()`経由で直接ダンプし、手計算した期待値と突き合わせる
5. **Act（修正・再キャプチャ）**: 1つの仮説につき1つの修正を行い、必ず再スクリーンショットで確認する。複数箇所を同時に直さない（今回、船が見えない問題を「カメラ距離」「船のスケール」「オービット中心」の3つの独立した仮説に分解し、1つずつ実測しながら直したことで、最終的な原因を取り違えずに済んだ）
6. **船体クローズアップ確認**: 見た目に関わる変更（特に船体の向き・回転・姿勢に関わるもの）は、最後に少なくとも1隻をズーム／近接視点でスクリーンショットし、船首の向きが速度ベクトル（進行方向）と一致しているか目視で確認してから完了とする。過去に発生した艏首90°ズレ（A-1）・航跡が空中に浮くバグ（A-3）はいずれも遠景の全体ショットだけでは気付けず、近接で見る観点が抜けていたために素通りした
7. **回帰確認**: 最後に複数の時間経過（オービット角度違い等）でスクリーンショットを取り、たまたま良く見えるフレームだけで判断していないか確認する

### 使い方

```bash
cd .devtools
MSYS_NO_PATHCONV=1 node screenshot.js /digital-twin/ ./out.png 5000
```

第1引数はパス、第2引数は出力先、第3引数は読み込み後の待機ミリ秒（アニメーションが落ち着くまで待つ）。

### この仕組みの位置づけ

- `.devtools/`はリポジトリに含めるが、`node_modules`とスクリーンショット画像自体はgit管理外にする（再現手順は残すが、バイナリ・依存物は残さない）
- これにより「動いていることの証拠」を自分で作れるようになり、見た目の確認のたびにユーザーに実機確認を依頼せず開発サイクルを回せる
- ただし最終的な「見た目として十分魅力的か」の主観判断はユーザー確認に委ねる。このメソッドが保証するのは「壊れていないこと」「意図通りの状態になっていること」まで

## 今後の適用ルール

- **見た目に関わる変更**（`scene_builder.js`、`landmarks.js`、`map_view.js`、`agent_view.js`等）は、コミット前に必ずスクリーンショットで確認する
- **座標変換・角度計算**（絶対方位⇔相対方位、ローカル座標⇔ワールド座標⇔緯度経度）は特に間違えやすいため、変更時は`debug.js`的なスクリプトで実測値を出力し、手計算した期待値と突き合わせる
- **`core/`のロジック変更**は自動テストが無いため、同様にワンオフ検証スクリプトで実測確認する習慣を続ける。将来的にテストフレームワークを導入する場合も、この「実測して期待値と比較する」考え方は維持する
- スクリーンショット確認は「壊れていないか」のスモークテストであり、フレームレート・実機GPU性能・実際のユーザー操作感までは保証しない。GPU本番環境での確認は別途必要
