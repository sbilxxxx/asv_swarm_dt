# 3D表現の品質向上計画

- 作成: 2026-08-07
- 対象: `digital-twin/`（3D海域DTビュー）
- 位置づけ: [`review-findings-2026-08-07.md`](review-findings-2026-08-07.md) が「正しく動いていない箇所」の一覧であるのに対し、
  本ドキュメントは「動いてはいるが品質が足りない箇所」の計画。
- **前提**: 品質向上は目的ではなく手段。GPU利用申請・ハッカソン審査で「計算資源を投じる価値がある基盤だ」と
  評価されるために必要な水準まで上げる、という位置づけ。過剰investmentは避ける（下記「やらないこと」参照）。

## 1. 現状の実測（2026-08-07時点）

### 1.1 頂点予算の配分

| 要素 | 頂点数 | 比率 |
|---|---|---|
| **海面（平面メッシュ）** | **25,921** | **83.3%** |
| お台場（島・フジテレビ・観覧車） | 1,110 | 3.6% |
| **船3隻（本作の主役）** | **1,311** | **4.2%** |
| レインボーブリッジ | 772 | 2.5% |
| ビル群30棟 | 720 | 2.3% |
| クレーン4基 | 672 | 2.2% |
| その他（陸地・東京タワー・倉庫・コンテナ船・富士山） | 615 | 2.0% |
| **合計** | **31,121** | |

### 1.2 ここから読み取れる2つの問題

**(a) 予算配分が主役と逆転している**

ほぼ平坦にしか見えない海面が全体の83%を占める一方、主役であるASVは3隻合計で4.2%（1隻あたり437頂点＝箱を数個組んだ量）。
近接ショットで船が「素のポリゴン塊」に見えるのはこのため。

**(b) そもそも総量が極端に少ない**

総頂点数31,121は、現代のGPUにとって極小（ゲームのキャラクター1体で5〜10万頂点、GPUは毎秒数千万頂点を処理する）。
**「重いから簡素にしている」のではなく、単に作り込んでいないだけ**。性能上の余裕は十分にある。

### 1.3 海面メッシュの解像度不足

| 項目 | 値 |
|---|---|
| 分割数 | 160 × 160（頂点25,921） |
| 実寸 | 9,000m × 9,000m |
| **1マスの大きさ** | **約56m** |
| 船の全長 | 14.7m（＝1マスの1/4） |

船が1マスより小さいため、**船の周囲の海面は実質的に平らな三角形1枚**。波の起伏は船のスケールでは全く表現されていない。

波の成分ごとの解像度（サンプリング定理上、滑らかに見せるには1波長あたり8〜10点必要）:

| 成分 | 波長 | 1波長あたりの格子点 | 判定 |
|---|---|---|---|
| 1 | 140m | 2.5点 | 不足 |
| 2 | 90m | **1.6点** | **表現不能（エイリアシング）** |
| 3 | 222m | 4.0点 | 不足 |

> **経緯の記録**: この解像度不足は、ブリッジカメラに水面の縁が映る問題を直すため
> 海面を3,420m→9,000mに広げた際、分割数を160のままにしたことで悪化した（1マス28.5m→56.3m）。
> 「片方を直して片方を壊す」典型例。スクリーンショット確認時に船が主役だったため見落とした。

### 1.4 影がほぼ機能していない

```
shadow.mapSize   = 1024 × 1024
shadow.camera    = ±1,900m（3,800m四方をカバー）
→ 影テクセル1個  = 3.7m
→ 船（14.7m）は影テクスチャ上でわずか4ピクセル
```

計算コストは払っているが、絵には「ぼやけた染み」以上に貢献していない。

### 1.5 曲面の分割数不足

| 部位 | 現状 | 見え方 |
|---|---|---|
| センサードーム | `SphereGeometry(r, 10, 6)` | 六角形の板の集合 |
| 航海灯 | `SphereGeometry(r, 8, 8)` | サイコロに近い |
| マスト | `CylinderGeometry(..., 6)` | 六角柱 |
| 船体の面取り | `bevelSegments: 1` | 一段の鋭い角 |

### 1.6 マテリアルの単調さ

- 全マテリアルが単色。テクスチャ・法線マップなし
- **環境マップ（envMap）が無い**ため、船体に設定した `metalness: 0.1` が意味を持たない（映り込む環境が存在しない）
- 遠景ランドマークが手前と同じコントラストで描かれ、大気遠近が効いていない

## 2. 再設計案

### 方針1: 海面の予算を船へ移す（LOD化）

カメラ近傍だけ細かく、遠方は粗くする。

| | 範囲 | 分割 | 頂点数 | 1マス |
|---|---|---|---|---|
| 現状 | 9,000m四方 | 160×160 | 25,921 | 56m |
| **提案（近傍）** | 600m四方 | 128×128 | 16,641 | **4.7m** |
| **提案（遠方）** | 9,000m四方 | 24×24 | 625 | 375m |
| | | **合計** | **17,266** | |

**現状比33%削減しながら、船の周囲は12倍精細になる。** 遠方の海面は水平線を埋める青い面でしかないため、粗くても破綻しない。

### 方針2: 船を主役の解像度にする

437頂点/隻 → **3,000〜5,000頂点/隻**（方針1の削減分で、隻数を15隻に増やしても吸収できる）。

- **船体形状**: 単一の平面形状を押し出す方式をやめ、**複数の断面を船首から船尾へ変化させる**
  （船首は尖って浅く、中央は幅広く深く、船尾は角ばる）。これだけで「箱」が「船」になる
- **面取り**: `bevelSegments` 1→3、球・円柱の分割数を2〜3倍
- **喫水線の塗り分け**: 実船は水線下が別色（防汚塗料の赤茶）。1要素で船らしさが大きく上がる
- **ディテール追加**: 手すり、デッキ上の機器、アンテナ、係船金物。小さな部品が数個あるだけで「作られた感」が出る

### 方針3: 影を実用にする

```
現状: 3,800m四方 / 1024px → 3.7m per texel
提案:   400m四方 / 2048px → 0.2m per texel（18倍精細）
```

影を**船の周辺だけ**に限定する。遠景の建物の影は元々見えないので捨てる。船と影が接地して見えるようになり「浮いている感」が消える。

### 方針4: 環境マップを導入

空のグラデーションから `PMREMGenerator` で環境マップを生成し、`scene.environment` に設定する。
**追加コストはほぼゼロで、全マテリアルの金属・光沢面が一気に本物らしくなる**（船体・センサードーム・窓ガラス）。

### 方針5: 「らしさ」を出す小要素

- **船首波（bow wave）**: 船首が水を切る白いV字。航跡より目立つ
- **大気遠近**: 遠景ほど霞ませ、コントラストを落とす
- **接地感の補強**: 船直下の薄い暗色（影が効くまでの代替）

## 3. 優先順位と工数

| # | 内容 | 工数 | 効果 | 状態 |
|---|---|---|---|---|
| 1 | 環境マップ導入 | 15分 | **大**（全マテリアルに効く） | 対応済（2026-08-07） |
| 2 | 影の範囲を船周辺に限定＋2048px | 15分 | 大（接地感） | 対応済（2026-08-07） |
| 3 | **船体の多断面化＋喫水線塗り分け＋分割数増** | 1.5時間 | **最大**（主役が主役に見える） | 対応済（2026-08-07） |
| 4 | 海面LOD（近傍細かく・遠方粗く） | 1時間 | 中（波が実際に見える） | 対応済（2026-08-07） |
| 5 | 船首波・デッキ部品追加 | 1時間 | 中 | 未着手 |

### 実装メモ（1・2, 2026-08-07）

- **環境マップ**: `createSkyTexture()`（空グラデーション）を`EquirectangularReflectionMapping`として`PMREMGenerator.fromEquirectangular()`に通し`scene.environment`へ設定。追加テクスチャなし。
- **影**: `sun.shadow.mapSize`を1024→2048、影カメラのボックスを±1900相当→±200（400m四方）に縮小し、`updateShips()`内で毎フレーム`updateShadowTarget()`を呼んでヒーロー艇の注視点（orbitTargetと同じ）に追従させるようにした。
- **影のハマりどころ（実測で発見・解消済み）**: 当初「影専用の透明メッシュ（`THREE.ShadowMaterial`）を水面の少し上に重ねる」案で実装したが、**影が一切映らない**不具合が発生。`devtools/diag_shadow_*.js`（一時ファイル、作業後に削除）でrenderer.info・shadow map実テクセル・シーングラフ走査による実測を行い、原因は「船体（水面から見て上下にまたがる立体）と、固定高さに置いた平らな受け面が幾何学的に交差し、その交差域で深度比較が破綻していた」ことと判明。
  - 正しい直し方は「水面メッシュ自身に影を受けさせる」こと。水面は自前の`ShaderMaterial`（波の頂点変位＋フレネル反射のカスタムシェーダー）なので、既存の`receiveShadow`は素通りする。Three.js組み込みのShaderChunk（`shadowmap_pars_vertex`/`shadowmap_vertex`/`shadowmap_pars_fragment`/`shadowmask_pars_fragment`）を`#include`し、`material.lights = true`＋`THREE.UniformsLib.lights`のマージ＋フラグメント側での`uniform bool receiveShadow;`明示宣言（レンダラーがオブジェクト単位でコンパイル済みプログラムへ直接setValueするため、宣言しないと「undeclared identifier」でコンパイルが落ちる）を行うことで解決。波の変位ジオメトリ・WAVE_TERMSには一切手を触れていない。
  - 影は完全な黒ではなく`mix(0.55, 1.0, shadow)`で海色に沈める程度に留めた（実際の水面の影は真っ黒にならないため）。

### 実装メモ（3, 2026-08-07）

- 単一断面のExtrudeGeometryを廃止し、船首〜船尾を9つの制御断面（`HULL_CONTROL`）で定義してSTATION_COUNT=60本の輪切りをロフトする方式に置き換えた（`buildHullGeometries()`）。断面は船尾＝角型トランサム、中央＝最大幅・最深、船首＝鋭く浅い、という指定通りの形状変化を持つ。
- **実測頂点数**: 1隻あたり437 → **3,975**（目標3,000〜5,000の範囲内）。船体3隻合計の全体比率は4.2% → 約28%（`qa-shots.js`のperShipVertices/grandTotalVerticesで実測、シーン合計は31,605→42,240）。
- **喫水線の塗り分け**: 各断面の「チャイン」（最大張り出し点）の高さを一律の基準に固定することで、上半分（船体色メッシュ）・下半分（防汚色メッシュ）を継ぎ目なく2メッシュに分割。分割境界の頂点座標は完全に共有しているためズレようがない。
- **ハマりどころ（実測で発見）**: チャインを物理喫水線ちょうどの高さに置くと、波の起伏・通常のカメラ角度では防汚色帯がほぼ常に水没して見えなかった。実船のボートトッピング帯にならい、喫水線よりわずか（0.16×SHIP_VISUAL_SCALE）上に固定して常時露出させた。さらに、この帯は太陽光に対して浅い角度になりやすい面のため、通常のMeshStandardMaterial陰影だけだとほぼ黒つぶれしていた（`gl.readPixels()`で実際のピクセル値を読み、R成分は優位でも絶対値が数%しかないことを確認）。彩度を上げた色＋軽いemissiveで解消。
- 分割数増: センサードーム（10,6→20,14）・航海灯（8,8→16,16）・マスト円柱（6→14）。
- 船体マテリアルは`side: THREE.DoubleSide`にした。ロフトの三角形巻き順を面ごとに手検証する代わりに両面描画で確実に穴を防ぐ判断（実測でこの判断に至った経緯: 喫水線下メッシュが最初「真っ黒」に見えるバグに遭遇し、`page.evaluate()`で法線・マテリアル・シャドウ設定を1つずつ実測して切り分けたところ、シャドウでも法線でもなく、単に幾何が正しく描画されている上で暗すぎただけと判明した）。
- デッキハウス・マスト・ステルス等の部品は、船体断面の甲板高さ（`hullProfileAtX()`）を参照して配置し直した。固定値のままだと新しい船体形状（船首尾で甲板高さが変わる）に対して浮いたり埋まったりするため。
- 針路と船首方向の整合性（コミット4735ad7の教訓）は、bow/beam/mid_shadowの各スクリーンショットで目視確認済み（+Xが船首のまま変えていない・座標変換は一切追加していない）。

### 実装メモ（4, 2026-08-07）

- 遠方パッチ: 9,000m四方のまま分割数を160×160→24×24に削減（625頂点）。近傍パッチ: 600m四方・128×128（16,641頂点）を新設し、`updateShips()`内でヒーロー艇の注視点（orbitTargetと同じ）に毎フレーム追従させる。近傍パッチはY方向にわずか(+0.02)高く置き、遠方パッチとの重なり域で確実に手前に描かれるようにした（スカート方式。計画の「重なりでもスカートでもよい」を採用）。
- **実測頂点数（水面合計）**: 25,933 → 17,278（分割は33%減）。シーン全体は33,585（船体多断面化後の42,240から、水面LODで再度削減）。
- **ハマりどころ①（実測で発見）**: 波の位相を水面メッシュの「ローカル座標」で評価していたため、近傍パッチ（動く）と遠方パッチ（固定）の原点が別々になった瞬間、同じワールド座標でも位相が食い違い、境界で波が食い違う設計になっていた（実装中に気づき、頂点シェーダーをワールド座標＝シミュレーション座標基準に直してから実装。JS側`waveHeightAt()`の呼び出し引数も同じ基準に合わせて修正——`center`によるオフセットを廃止）。
- **ハマりどころ②（実測で発見）**: 波の可視性を上げようと振幅を約1.7倍（合計最大0.87→1.45）にしたところ、フラグメントシェーダー側の `crest = clamp(vWave*0.5+0.5, 0, 1)` が `vWave` を暗黙に「振幅合計は最大でも1」という前提で正規化していたため、振幅を上げるほどclampで階調が潰れ、むしろ波が見えにくくなるという逆効果が発生した（`gl.readPixels()`でcrest値を直接可視化して発見）。`WAVE_AMPLITUDE_SUM`（WAVE_TERMSから導出、JS/シェーダー間で共有）で正規化するよう修正し、階調を0..1いっぱいに使うようにした。
- 波の見た目のコントラストを上げるため、フラグメント側で`vWave`に基づく明度変調（`color *= 0.82 + 0.36 * crest`）を追加。鏡面反射（exponent=70の非常に狭いハイライト）だけでは、実際の波の傾き（1〜2度程度）では起伏がほぼ見えなかったため。
- 近傍・遠方の境界（船から300m）を実際にカメラで跨いでスクリーンショット確認したが、波の高さが一致しているため継ぎ目のひび割れ・段差は見えない。

**1と2は合計30分で効果が大きい**ため、着手するならここから。**3が本命**。

## 4. やらないこと（意図的なスコープ外）

- **波の物理的忠実性の追求**。波はシミュレーションに一切影響していない（`environment.sample()` は運動学から呼ばれてすらいない、
  [`review-findings-2026-08-07.md`](review-findings-2026-08-07.md) B-3参照）。純粋な見た目でしかないものに、
  サンプリング定理レベルの整合を求めない。**方針1は「船の周りで波が見える」ところまでで打ち切る**
- **テクスチャ・法線マップの導入**。外部アセット依存が生じ、「ビルド不要・サーバー不要」（NFR2）を壊す
- **物理ベースの流体・砕波表現**。現在の2.5Dハイトフィールド方式（各座標に高さが1つ決まる）を超える表現は目的に対して過剰

> **波が意味を持つ将来段階**: 「波高が高いとASVの制御が乱れる」「レーダーに海面クラッタが乗る」など、
> シミュレーションに効く段階になって初めて忠実性が必要になる。それはサロゲートモデル導入時の話であり、現段階ではない。

## 5. 全体計画における位置づけ（重要）

3D品質向上に着手する前に、**プロジェクトの看板と中身の乖離**を認識しておくこと。

| 看板 | 実態 |
|---|---|
| マルチASV**スウォーム** | 3隻。スウォームと呼べる数ではない |
| **フィジカルAI**（LLM/VLM/VLA） | **AIのコードが1行もない**。ルールベースのみ |
| **攻防**シミュレーション | 勝敗条件なし。互いに追いかけ回すだけ |
| GPUを回す価値 | **GPUで回す推論対象が存在しない** |

「AIエージェント社会シミュレーションハッカソン」への応募で **AIエージェントが実装されていない**のは、
3DCGの品質より優先度が高い課題である。

**推奨する全体の順序**:

1. **攻防の成立**（`core/sim/mission.js` の EnvApi への配線）— 半日。追いかけっこが攻防になり、報酬・エピソード反復が揃う
2. **隻数を増やす**（3隻→20〜30隻）— シナリオJSONの記述増で概ね済む。「スウォーム」の絵が初めて成立する
3. **headlessランナー**— ブラウザの60ステップ/秒制約を外す。Node上ならOllama/APIを叩けるため次項の前提になる
4. **LLMエージェントを実際に動かす**— `decideFn` にOllama呼び出しを差す。「GPUで推論を回す」の実体ができる
5. **本ドキュメントの3D品質向上**（優先度1→2→3の順）

ただし本計画の**優先度1・2（環境マップ・影）は合計30分**なので、上記1〜4の合間に差し込んでも構わない。
