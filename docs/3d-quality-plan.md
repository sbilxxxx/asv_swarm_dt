# 3D表現の品質向上計画

- 作成: 2026-08-07
- 対象: `digital-twin/`（3D海域DTビュー）
- 位置づけ: [`review-findings-2026-08-07.md`](review-findings-2026-08-07.md) が「正しく動いていない箇所」の一覧であるのに対し、
  本ドキュメントは「動いてはいるが品質が足りない箇所」の計画。
- **前提**: 品質向上は目的ではなく手段。GPU利用申請・ハッカソン審査で「計算資源を投じる価値がある基盤だ」と
  評価されるために必要な水準まで上げる、という位置づけ。過剰investmentは避ける（下記「やらないこと」参照）。

---

## 1. 現状の実測（2026-08-07時点）

### 1.1 頂点予算の配分

| 要素 | 頂点数 | 比率 |
|---|---|---|
| **海面（平面メッシュ）** | **25,921** | **83.3%** |
| お台場（島・フジテレビ・観覧車） | 1,110 | 3.6% |
| **船3隻（本作の主役）** | **1,311** | **4.2%** |
| レインボーブリッジ | 772 | 2.5% |
| ビル群30棟 | 720 | 2.3% |
| クレーン4基 | 672 | 2.2% |
| その他（陸地・東京タワー・倉庫・コンテナ船・富士山） | 615 | 2.0% |
| **合計** | **31,121** | |

### 1.2 ここから読み取れる2つの問題

**(a) 予算配分が主役と逆転している**

ほぼ平坦にしか見えない海面が全体の83%を占める一方、主役であるASVは3隻合計で4.2%（1隻あたり437頂点＝箱を数個組んだ量）。
近接ショットで船が「素のポリゴン塊」に見えるのはこのため。

**(b) そもそも総量が極端に少ない**

総頂点数31,121は、現代のGPUにとって極小（ゲームのキャラクター1体で5〜10万頂点、GPUは毎秒数千万頂点を処理する）。
**「重いから簡素にしている」のではなく、単に作り込んでいないだけ**。性能上の余裕は十分にある。

### 1.3 海面メッシュの解像度不足

| 項目 | 値 |
|---|---|
| 分割数 | 160 × 160（頂点25,921） |
| 実寸 | 9,000m × 9,000m |
| **1マスの大きさ** | **約56m** |
| 船の全長 | 14.7m（＝1マスの1/4） |

船が1マスより小さいため、**船の周囲の海面は実質的に平らな三角形1枚**。波の起伏は船のスケールでは全く表現されていない。

波の成分ごとの解像度（サンプリング定理上、滑らかに見せるには1波長あたり8〜10点必要）:

| 成分 | 波長 | 1波長あたりの格子点 | 判定 |
|---|---|---|---|
| 1 | 140m | 2.5点 | 不足 |
| 2 | 90m | **1.6点** | **表現不能（エイリアシング）** |
| 3 | 222m | 4.0点 | 不足 |

> **経緯の記録**: この解像度不足は、ブリッジカメラに水面の縁が映る問題を直すため
> 海面を3,420m→9,000mに広げた際、分割数を160のままにしたことで悪化した（1マス28.5m→56.3m）。
> 「片方を直して片方を壊す」典型例。スクリーンショット確認時に船が主役だったため見落とした。

### 1.4 影がほぼ機能していない

```
shadow.mapSize   = 1024 × 1024
shadow.camera    = ±1,900m（3,800m四方をカバー）
→ 影テクセル1個  = 3.7m
→ 船（14.7m）は影テクスチャ上でわずか4ピクセル
```

計算コストは払っているが、絵には「ぼやけた染み」以上に貢献していない。

### 1.5 曲面の分割数不足

| 部位 | 現状 | 見え方 |
|---|---|---|
| センサードーム | `SphereGeometry(r, 10, 6)` | 六角形の板の集合 |
| 航海灯 | `SphereGeometry(r, 8, 8)` | サイコロに近い |
| マスト | `CylinderGeometry(..., 6)` | 六角柱 |
| 船体の面取り | `bevelSegments: 1` | 一段の鋭い角 |

### 1.6 マテリアルの単調さ

- 全マテリアルが単色。テクスチャ・法線マップなし
- **環境マップ（envMap）が無い**ため、船体に設定した `metalness: 0.1` が意味を持たない（映り込む環境が存在しない）
- 遠景ランドマークが手前と同じコントラストで描かれ、大気遠近が効いていない

## 2. 再設計案

### 方針1: 海面の予算を船へ移す（LOD化）

カメラ近傍だけ細かく、遠方は粗くする。

| | 範囲 | 分割 | 頂点数 | 1マス |
|---|---|---|---|---|
| 現状 | 9,000m四方 | 160×160 | 25,921 | 56m |
| **提案（近傍）** | 600m四方 | 128×128 | 16,641 | **4.7m** |
| **提案（遠方）** | 9,000m四方 | 24×24 | 625 | 375m |
| | | **合計** | **17,266** | |

**現状比33%削減しながら、船の周囲は12倍精細になる。** 遠方の海面は水平線を埋める青い面でしかないため、粗くても破綻しない。

### 方針2: 船を主役の解像度にする

437頂点/隻 → **3,000〜5,000頂点/隻**（方針1の削減分で、隻数を15隻に増やしても吸収できる）。

- **船体形状**: 単一の平面形状を押し出す方式をやめ、**複数の断面を船首から船尾へ変化させる**
  （船首は尖って浅く、中央は幅広く深く、船尾は角ばる）。これだけで「箱」が「船」になる
- **面取り**: `bevelSegments` 1→3、球・円柱の分割数を2〜3倍
- **喫水線の塗り分け**: 実船は水線下が別色（防汚塗料の赤茶）。1要素で船らしさが大きく上がる
- **ディテール追加**: 手すり、デッキ上の機器、アンテナ、係船金物。小さな部品が数個あるだけで「作られた感」が出る

### 方針3: 影を実用にする

```
現状: 3,800m四方 / 1024px → 3.7m per texel
提案:   400m四方 / 2048px → 0.2m per texel（18倍精細）
```

影を**船の周辺だけ**に限定する。遠景の建物の影は元々見えないので捨てる。船と影が接地して見えるようになり「浮いている感」が消える。

### 方針4: 環境マップを導入

空のグラデーションから `PMREMGenerator` で環境マップを生成し、`scene.environment` に設定する。
**追加コストはほぼゼロで、全マテリアルの金属・光沢面が一気に本物らしくなる**（船体・センサードーム・窓ガラス）。

### 方針5: 「らしさ」を出す小要素

- **船首波（bow wave）**: 船首が水を切る白いV字。航跡より目立つ
- **大気遠近**: 遠景ほど霞ませ、コントラストを落とす
- **接地感の補強**: 船直下の薄い暗色（影が効くまでの代替）

## 3. 優先順位と工数

| # | 内容 | 工数 | 効果 | 状態 |
|---|---|---|---|---|
| 1 | 環境マップ導入 | 15分 | **大**（全マテリアルに効く） | 未着手 |
| 2 | 影の範囲を船周辺に限定＋2048px | 15分 | 大（接地感） | 未着手 |
| 3 | **船体の多断面化＋喫水線塗り分け＋分割数増** | 1.5時間 | **最大**（主役が主役に見える） | 未着手 |
| 4 | 海面LOD（近傍細かく・遠方粗く） | 1時間 | 中（波が実際に見える） | 未着手 |
| 5 | 船首波・デッキ部品追加 | 1時間 | 中 | 未着手 |

**1と2は合計30分で効果が大きい**ため、着手するならここから。**3が本命**。

## 4. やらないこと（意図的なスコープ外）

- **波の物理的忠実性の追求**。波はシミュレーションに一切影響していない（`environment.sample()` は運動学から呼ばれてすらいない、
  [`review-findings-2026-08-07.md`](review-findings-2026-08-07.md) B-3参照）。純粋な見た目でしかないものに、
  サンプリング定理レベルの整合を求めない。**方針1は「船の周りで波が見える」ところまでで打ち切る**
- **テクスチャ・法線マップの導入**。外部アセット依存が生じ、「ビルド不要・サーバー不要」（NFR2）を壊す
- **物理ベースの流体・砕波表現**。現在の2.5Dハイトフィールド方式（各座標に高さが1つ決まる）を超える表現は目的に対して過剰

> **波が意味を持つ将来段階**: 「波高が高いとASVの制御が乱れる」「レーダーに海面クラッタが乗る」など、
> シミュレーションに効く段階になって初めて忠実性が必要になる。それはサロゲートモデル導入時の話であり、現段階ではない。

## 5. 全体計画における位置づけ（重要）

3D品質向上に着手する前に、**プロジェクトの看板と中身の乖離**を認識しておくこと。

| 看板 | 実態 |
|---|---|
| マルチASV**スウォーム** | 3隻。スウォームと呼べる数ではない |
| **フィジカルAI**（LLM/VLM/VLA） | **AIのコードが1行もない**。ルールベースのみ |
| **攻防**シミュレーション | 勝敗条件なし。互いに追いかけ回すだけ |
| GPUを回す価値 | **GPUで回す推論対象が存在しない** |

「AIエージェント社会シミュレーションハッカソン」への応募で **AIエージェントが実装されていない**のは、
3DCGの品質より優先度が高い課題である。

**推奨する全体の順序**:

1. **攻防の成立**（`core/sim/mission.js` の EnvApi への配線）— 半日。追いかけっこが攻防になり、報酬・エピソード反復が揃う
2. **隻数を増やす**（3隻→20〜30隻）— シナリオJSONの記述増で概ね済む。「スウォーム」の絵が初めて成立する
3. **headlessランナー**— ブラウザの60ステップ/秒制約を外す。Node上ならOllama/APIを叩けるため次項の前提になる
4. **LLMエージェントを実際に動かす**— `decideFn` にOllama呼び出しを差す。「GPUで推論を回す」の実体ができる
5. **本ドキュメントの3D品質向上**（優先度1→2→3の順）

ただし本計画の**優先度1・2（環境マップ・影）は合計30分**なので、上記1〜4の合間に差し込んでも構わない。
